# 拾序：默认目录、项目目录与外部授权改造说明

这次保留 `create_deep_agent`，把文件工作区从“所有会话共用一个目录”改为“每次运行从服务端确定工作目录和授权”。模型负责理解任务和文件名，程序负责确定文件落点与访问权限。

## 在界面里怎么用

1. 打开 **设置 → 工作目录**，选择默认工作目录并保存。普通会话在这里读写文件。初始值沿用原来的 `agent-files/`，可以输入绝对路径，也可以浏览本机目录。
2. **创建项目**时填写名称并选择项目工作目录。该项目里的会话使用该目录。已有旧项目会提示设置目录，不会悄悄使用默认目录。
3. 进入一个会话，顶部会显示真实工作目录。打开 **目录与授权**，可以选择一个外部文件或目录，授予**只读**或**读写**权限，也可以撤销授权。

外部授权只属于当前会话，保存在本地，重启后仍在，直到撤销或删除会话。撤销授权只移除访问资格，不删除用户文件。任务运行中需要先停止或等待完成，再修改目录或授权。

默认目录、项目目录和授权路径必须是本机后端可访问的真实文件或目录。修改目录后，后续任务使用新目录，已有文件仍留在原位置；程序不会自动搬迁文件。

## 路径怎样决定

每个会话只有一个当前工作目录：

```text
普通会话 → 默认工作目录
项目会话 → 该项目的工作目录

报告.md 或 ./报告.md
    → /workspace/报告.md
    → 当前真实工作目录/报告.md

其他绝对路径
    → 检查是否属于当前目录或当前会话的外部授权
    → 未授权：返回明确错误，等待用户在界面授权
```

授权目录通过 `/external/<授权ID>/` 提供给 Agent；授权单个文件时，路径为 `/external/<授权ID>/<文件名>`，不会连带授权同目录的其他文件。已授权的真实绝对路径也可以作为别名使用。外部资料的读取位置不会改变新产物的默认保存位置。

路径不存在、项目未配置或目录指向发生变化时，会明确报错，不会自动退回默认目录。用户文件路径也不会悄悄变成只存在于会话状态里的文件。

## 后端改了什么

### `backend/app/workspaces.py`

定义 `WorkspaceSnapshot`、`WorkspaceGrant` 和 `ShixuContext`，并集中校验本机路径、提供目录选择器所需的文件名列表。

`WorkspaceSnapshot` 相当于一次任务的环境清单：当前项目、实际根目录、外部授权和内部保护路径。它由后端数据库查询产生，不采用浏览器或模型自行声明的权限。

### `backend/app/storage.py`

新增默认工作目录设置、会话外部授权记录，并给项目表增加 `workspace_path`。迁移采用新增表和新增列，保留原有项目、对话和模型配置。旧项目的目录为空，等待用户选择。

这些本机路径和授权记录保存在 `data/workspace.db` 中，该目录已被 Git 忽略。

### `backend/app/main.py`

增加工作目录配置、目录浏览、项目目录设置、授权与撤销接口。

模型任务开始前，按下面的链路生成工作区快照：

```text
会话 ID → 会话所属项目 → 项目目录或默认目录 → 当前会话的授权
```

每次模型运行构建独立的文件后端与 Agent 图，继续共用原来的模型配置及 SQLite 检查点。不会为了切换项目而修改一个全局 `root_dir`。

AG-UI 当前版本通过请求级 `clone.config['configurable']['workspace']` 把后端快照传给 LangGraph 的 `runtime.context`。客户端传来的 state、工具、context 和 forwarded props 继续被清空，不能用来修改目录授权。

### `backend/app/deep_agent.py`

增加 `context_schema=ShixuContext` 和 `@dynamic_prompt`。每次模型调用时，从 `request.runtime.context['workspace']` 读取环境，在保留原系统提示的基础上追加项目、目录和授权说明，不把环境消息反复写进聊天历史。

同一份配置同时用于构造真实文件后端。提示词中的环境必须和后端快照一致，否则拒绝该次调用。

增加路径处理中间件，在 Deep Agents 对路径做统一处理之前，把原始相对路径转成 `/workspace/...`。这一步保证普通文件名的落点由代码确定。

显式配置 `general-purpose` 子 Agent，让主、子 Agent 使用同一个文件后端、路径处理中间件和动态环境提示。当前 Deep Agents 版本不会自动把所有新增中间件传给默认子 Agent，因此需要这段显式装配。

### `backend/app/workspace_backend.py`

继续复用官方 `FilesystemBackend` 做磁盘操作，外层用 `CompositeBackend` 路由当前工作区、外部授权及框架内部文件。

权限检查发生在工具执行端：

- 只读授权拒绝新建、编辑与上传写入，包括异步入口。
- 单文件授权不能访问相邻文件。
- 路径越界、指向未授权位置的符号链接、授权后被替换的目录或文件会被拒绝。
- 应用自身的数据库、密钥文件和运行环境不能通过文件工具访问；搜索在读取文件前排除保护目录。
- 仅实际框架使用的 `/large_tool_results/`、`/conversation_history/`、`/blobs/` 进入 `StateBackend`。
- 主、子 Agent 都只开放列目录、读取、新建、编辑、文件名搜索、内容搜索六种文件工具。没有删除或终端工具，后端删除入口也继续直接拒绝。

这是本机应用的路径与权限限制，不是操作系统级沙箱；本次没有增加终端执行能力。

## 前端改了什么

- `workspace-settings.tsx`：默认工作目录配置。
- `directory-picker.tsx`：只请求本机 macOS 系统选择窗口，不渲染网页弹窗。选中后回填真实路径，取消保留原表单，失败信息显示在原表单里。
- `workspace-access.tsx`：当前目录展示、项目目录设置、会话外部授权及撤销。
- `workspace.tsx`：项目创建必选目录，成功后自动在该项目下创建并打开首个会话；另提供旧项目配置入口、工作区不可用时禁用发送、移动会话时说明后续目录变化。自动会话与“新建任务”共用创建和选中逻辑，明确传入新项目 ID；若会话创建失败，保留已经创建的项目并提示通过“新建任务”重试。
- `model-settings.tsx`：设置导航增加工作目录，保留未保存更改的离开确认。
- 后端代理：校验修改请求的来源，避免其他网页借本地代理创建文件授权。

创建项目后自动进入会话的顺序是：先取得新项目接口返回的 ID，再把这个 ID 直接传给共享的 `createConversation()`，创建会话并设置选中状态。这里不能先调用 `setCurrentProject()` 后马上读取 `currentProject`，因为 React 的状态更新不会立即改变当前函数中的旧值。“新建任务”也复用这个函数；按钮的忙碌状态由各自入口控制。

### 删除项目如何保留会话和文件

项目行的“⋯ → 删除项目”会打开确认弹窗。`storage.py` 在同一 SQLite 事务内将所属会话的 `project_id` 设为 `NULL`，再删除项目记录；任何一步失败都会回滚。会话 ID、标题、置顶、消息、外部授权以及另外两份数据库中的运行记录和检查点均保留，也不会调用磁盘删除操作。

`main.py` 的 `DELETE /api/projects/{project_id}` 拒绝本项目内正在执行的任务；Next.js 代理另检查运行库中的排队标记。为避免“检查完忙碌状态后，新任务又同时入队”的时间差，当前 Next.js 进程共享一份运行与删除协调状态：运行请求在查询会话前先预留位置，删除项目在读取成员至后端完成期间持有该项目的删除标记。两边相互检查，运行预留到响应流结束或取消才释放，错误也会清理。其他项目的任务不影响当前项目删除。

前端移除项目行，将会话显示到未分组；当前会话保持打开，并重新加载默认工作目录。后续 `Runtime context` 从服务端查询新的归属，因此下一轮使用默认目录。

删除失败时，确认弹窗保留并显示错误，可重试或取消；成功后清理旧项目引用，旧轮询响应不会重新显示已删项目。本机界面仅检查菜单、确认文案和取消；真实删除链路使用隔离测试项目验收。[本机确认界面](project-delete-preview.jpg)。

项目删除增量验证：107 项后端测试、前端类型检查、25 项隔离浏览器流程和 9 项运行协调单元检查通过。后端检查原子事务、检查点与下一轮默认上下文；浏览器使用真实临时数据库和磁盘，模型为本地 fixture，验证历史、置顶、授权、文件保留、手机操作和排队标记；协调单元用确定性的 Promise 门闩验证竞争顺序及响应流结束／错误／取消时释放。已有本机数据仅用于界面预览，没有执行项目删除或调用真实模型。

## 如何理解 Runtime context 与 dynamic_prompt

```text
服务端生成 WorkspaceSnapshot
          ├──→ 独立文件后端：执行真实路径和权限检查
          └──→ Runtime context
                    └──→ dynamic_prompt
                              └──→ SystemMessage → LLM
```

Runtime context 是程序数据，不会自动成为模型消息。`dynamic_prompt` 是把这些数据展示给模型的机制。`SystemMessage` 则是最终发给模型的消息对象。权限最终由代码执行，不由提示词授予。

以“在项目 A 中保存摘要.md”为例：

1. `main.py` 从会话找到项目 A，查询其真实目录与该会话授权。
2. `build_deep_graph(workspace=...)` 用快照构造文件后端；AG-UI 把同一快照传入 `runtime.context['workspace']`。
3. `@dynamic_prompt` 读取快照，告诉模型当前项目及 `/workspace/` 的实际对应目录。
4. 模型调用 `write_file(file_path='摘要.md', content=...)`。
5. `WorkspacePathMiddleware` 将它确定为 `/workspace/摘要.md`，文件后端检查权限后写入项目 A 的真实目录。

模型即使传入外部绝对路径，也必须经过第 5 步的授权检查。即使主 Agent 把任务委派给子 Agent，同样经过这条链路。

## macOS 系统目录选择增量

根据用户提供的 Finder 风格截图，三个位置的“浏览”统一调用 macOS 的 `NSOpenPanel`：默认工作目录、创建／设置项目目录、外部路径授权。前两个只选目录，外部授权允许文件或目录；系统负责侧栏、列表、搜索、路径导航及新建文件夹的外观与交互。

调用链是：`directory-picker.tsx` 发起 POST → Next.js 本地代理 → `main.py` 的 `/api/filesystem/pick` → `native_picker.py` 启动固定 JXA → `native_picker.js` 调用 AppKit → 返回选择路径 → 原表单回填。浏览器本身不能凭一个上传控件获得任意本机目录的绝对路径，因此这里借助已在本机运行的 Python 后端。

这一步只负责“选中”，保存默认目录、创建项目、确认外部授权仍由原来的提交按钮完成。系统取消保留原输入；关闭原表单或离开设置会中止后端选择进程。一次只允许一个选择窗口，期间禁用原浏览按钮和提交动作；结束后还焦原浏览按钮。失败显示在原路径字段附近，用户可再次点击“浏览”或手动输入。

后端仅接受本机调用，并检查请求来源；返回结果再次经过原有路径与内部保护范围校验。JXA 在后端导入时冻结为固定文本，路径、标题等通过独立参数传入，不拼接成脚本或 shell 命令。它是界面桥接，不是提供给 Agent 的执行工具；Agent 仍不能删除文件或使用终端。

系统选择窗口仅适用于后端运行在本机已登录桌面中的 macOS。后端在 Linux、容器或远程服务器上时，页面保留手动填写绝对路径的方式；路径始终属于后端机器。

增量验收：后端共 102 项、前端类型检查、生产构建通过，隔离浏览器共 20 项通过。浏览器用例模拟系统窗口的返回值，之后的目录保存、授权与文件读写走真实临时后端；覆盖取消、失败重试、重复请求防护、文件选择和移动端等待状态。系统桥接单元测试模拟子进程，另以不打开窗口的 JXA 参数回显核对中文、引号及参数分隔。没有调用真实模型。

本机页面已实际触发选择请求并验证网页取消后保留表单；当前自动化工具无法可靠定位独立 `osascript` 进程的窗口，因此未把系统窗口外观及在窗口内点击“打开／取消”记为自动验收通过，需本机人工确认。

后续按用户反馈去掉网页上的“请在系统窗口中选择目录”等待层。本机页面检查确认，点击项目目录“浏览”后只保留原创建项目表单，未叠加任何网页选择弹窗；[实际页面截图](workspace-native-only.jpg)仅记录网页状态，不包含系统窗口。此次前端类型检查与 21 项隔离浏览器检查通过，新增覆盖默认目录零弹窗、项目／授权仅原表单、取消保留草稿、错误重试及还焦；本机 Web 返回 200，未重启后端或修改已有业务数据。
